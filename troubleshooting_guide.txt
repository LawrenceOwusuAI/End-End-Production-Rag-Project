
PRODUCTION-GRADE RAG TROUBLESHOOTING PLAYBOOK — UBUNTU
Follow this order during an incident.

1. CONTAINER
  Is it running?
Description:
   Show all services in the current Compose project.
Expected:
     All important services should show Up.
docker compose ps

Description:
  Show all services including stopped/exited containers.
Expected:
  Useful for spotting crashed services.
docker compose ps -a

Description:
   Show all running Docker containers globally.
Expected:
  Containers such as:
# rag-backend
# rag-frontend
# prometheus
# alertmanager
# prometheus-mcp
# opensearch-mcp
# observability-agent
# otel-collector
# data-prepper
# cadvisor
docker ps


# Description:
# Show exited containers.
# Expected:
# Ideally empty.
docker ps -a --filter status=exited


# Description:
# Show restarting containers.
# Expected:
# Ideally empty.
docker ps --filter status=restarting


# Description:
# Show unhealthy containers.
# Expected:
# Ideally empty.
docker ps --filter health=unhealthy


# Description:
# Check restart count for rag-backend.
# Expected:
# Usually 0.
docker inspect rag-backend --format '{{.RestartCount}}'


# Description:
# Check restart count for observability-agent.
# Expected:
# Usually 0.
docker inspect observability-agent --format '{{.RestartCount}}'


# Description:
# Check restart count for prometheus-mcp.
# Expected:
# Usually 0.
docker inspect prometheus-mcp --format '{{.RestartCount}}'


# Description:
# Restart one unhealthy service.
# Expected:
# Service restarts successfully.
docker compose restart rag-backend


# Description:
# Recreate one service if restart is not enough.
# Expected:
# Container is replaced and starts again.
docker compose up -d --force-recreate --no-deps rag-backend


# Description:
# Restart the entire stack if necessary.
# Expected:
# All Compose services restart.
docker compose restart

REM =====================================================================
REM QUICK INCIDENT DECISION TREE
REM =====================================================================

REM If docker compose ps shows container missing/exited:
REM -> Fix container/startup first.

REM If container is Up but /health fails:
REM -> Investigate process/application startup.

REM If health works but service-to-service call fails:
REM -> Investigate Docker network/DNS.

REM If network works but request fails:
REM -> Read application logs.

REM If application works but monitoring is wrong:
REM -> Check metrics and Prometheus targets.

REM If targets are UP but no alert:
REM -> Check Prometheus rules and thresholds.

REM If Prometheus says firing but Alertmanager returns []:
REM -> Fix Prometheus -> Alertmanager delivery.

REM If Alertmanager has alert but agent has no /alerts/prometheus POST:
REM -> Fix Alertmanager webhook -> agent.

REM If agent receives webhook but no MCP traffic:
REM -> Fix MCP tool registration/connectivity.

REM If MCP investigation succeeds but no email:
REM -> Fix SMTP/email notification.

    Descripion of project
    """I built an end-to-end production-oriented RAG platform using FastAPI and Streamlit,
     containerized as microservices with Docker Compose. 
     I instrumented the system with OpenTelemetry and Prometheus, 
     implemented infrastructure and application metrics, alert rules 
     and Alertmanager-based alert routing, and built MCP servers that 
     expose controlled Prometheus and OpenSearch observability tools to 
     a LangChain agent. When a production threshold is breached, 
     Alertmanager sends the event to the observability agent, 
     which investigates the incident using metrics and traces and 
     automatically sends an email notification with the findings."""
